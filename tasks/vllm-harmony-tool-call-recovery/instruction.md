We run a long-context web-search agent on gpt-oss-120b through vLLM. The request declares a `webSearch` function, and the model stops for a tool call, but about half of repeated Chat Completions responses contain no `tool_calls`. The raw Harmony output in those failures names the recipient as `webSearch` instead of `functions.webSearch`; we have also observed otherwise valid calls emitted on `analysis` or `comment` rather than `commentary`.

The prefixed `functions.webSearch` form is returned correctly. With the bare form, Chat Completions silently drops the call, while the Responses API can classify it as an MCP call even though `webSearch` is one of the request’s declared functions. Built-in Harmony recipients such as `browser.search`, `python`, and `container` must not become user function calls.

Investigate and fix the inconsistent tool-call handling. Streaming and non-streaming Chat Completions and Responses requests should expose the declared function call regardless of the Harmony channel or optional `functions.` prefix, without reclassifying built-ins, assistant messages, special-token recipients, unknown recipients when an explicit tool list is present, or requests with an empty tool list.
